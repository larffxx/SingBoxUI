# ADR 011 — Routing rules that select an application by name (macOS)

## Context

The routing rules of a profile are address-based: a domain, a prefix, a port, a rule-set. That is how
sing-box matches, but it is not how a user thinks about a VPN. The question is "Chrome through the
tunnel, everything else directly", and the answer available in the UI was a domain list — which is
not the same thing, because one application talks to many domains and one domain answers many
applications. The legacy prototype had a split-tunneling helper that offered `process` among its
conditions (feature matrix row 6) and the rewrite dropped it.

The user's own working configuration contains the workaround: hand-written rules such as
`{"action": "route", "process_path_regex": [".*Telegram\\.app/.*"]}`.

What sing-box offers on macOS (1.14.0, verified against the source of `sing-box` and by running it):

* `process_name` matches `filepath.Base` of the executable path, `process_path` matches the path
  exactly, `process_path_regex` matches it as a regular expression. All three are supported on
  macOS (`common/process/searcher_darwin_shared.go`, `route/rule/rule_item_process_*.go`).
* The path comes from `proc_pidpath` for the process that owns the source address of the connection,
  so it is the path of the **main executable inside the bundle** (`/Applications/Telegram.app/
  Contents/MacOS/Telegram`), and helper processes inside the same bundle appear with their own paths
  there. The lookup works for an unelevated sing-box, and it resolves the real path: a bundle reached
  through a symlink reports the target (observed: `/tmp/...` is reported as `/private/tmp/...`).

Two facts follow, and both are easy to get wrong: an expression anchored at the *bundle* matches the
application and its helpers, and an expression written against an unresolved path never matches at
all. A rule is unusable without an application to write it from — and macOS, unlike Windows, has a
place where the installed applications are enumerated: `*.app` bundles in `/Applications`,
`/Applications/Utilities`, `/System/Applications`, `/System/Applications/Utilities` and
`~/Applications`.

## Decision

The application screen lives in the routing tab, and the list of applications comes from the OS.

* `internal/domain/applications` holds the value type: `Name`, `BundleID`, `Path`, `Executable` and
  `ProcessPathRegex`. It is flat and made of strings, so both the OS package and the frontend can
  carry it without deriving anything.
* `internal/platform` gains the port `ApplicationCatalog` (`Supported`, `UnsupportedReason`, `List`)
  and `Platform.Applications()`. `internal/platform/darwin` implements it: it scans the five
  directories, reads each bundle's `Info.plist` through `/usr/bin/plutil -convert json` (the only
  reader that handles the binary plist format nearly every bundle ships), resolves the bundle path,
  and derives the expression `^<resolved path>/` with every metacharacter quoted. The listing is
  cached for two minutes and errors are only reported when nothing at all could be listed.
* `internal/app/apps` is the use case: it answers with the applications, or — on a platform that
  cannot list them — with `Supported: false` and a reason. That is an answer, not an error: the
  screen explains itself and the rest of the profile keeps working. `AppsAPI` binds it to the
  frontend (ADR 002).
* The frontend writes ordinary routing rules. `frontend/src/features/profiles/appRules.ts` is the
  whole rule logic, pure and covered on its own: a new rule is **appended** (rules are evaluated in
  order, and nothing may silently take priority over the rules the user wrote by hand), switching an
  application rewrites the `outbound` of its rule, and clearing one removes its expression — and the
  rule with it when nothing else was left, because an action and an outbound without a condition
  would route the whole machine.
* The card is a view of the document, not a second bookkeeping: whether an application is "через
  VPN" or "напрямую" is read back out of `route.rules` on every render.
* `process_name`, `process_path` and `process_path_regex` become editable fields of the rule editor,
  so a rule generated by the card is not a black box and Windows users (where the catalog reports
  itself unsupported) can write the same kind of rule by hand.
* Windows has no equivalent list: programs are installed anywhere and the registry describes
  installers, not the process a user launches. The Windows catalog reports `Supported: false` and
  says what to do instead; nothing is guessed.

## Alternatives

* **Match on the display name** ("Telegram") — a bundle's display name is not what `proc_pidpath`
  reports; the rule would have to translate a name into a path anyway, and it would do so invisibly.
  Rejected.
* **`process_name` alone** — matches only the main executable (`filepath.Base` of its path), so
  Chrome's helpers, Electron's renderers and XPC services of the bundle stay outside the rule.
  Offered as a manual field instead.
* **`process_path`** — exact match on the executable path, with no wildcard support in sing-box;
  a rule breaks on the first helper process. Rejected as the generated form.
* **A rule-set built from the application list** — the list is machine-specific, and a rule-set is
  shared, cached and versioned; a lookup that depends on the local disk does not belong in one.
  Rejected.
* **Listing applications without a bundle identifier** (scanning `Contents/MacOS`) — every helper
  binary would become a row the user cannot recognise. Rejected.

## Consequences

* Adding an application is one click and produces a rule the user can read, edit and reorder like any
  other. The expression is anchored at the bundle, so helpers are covered, and it is resolved, so it
  matches what sing-box reports.
* A rule follows the *location* of the bundle: moving an application to another folder or installing
  it somewhere not scanned leaves the rule behind. The card says so, and the fix is one click.
* The listing costs one `plutil` per bundle (~80 on a typical Mac, ~0.05 s with eight workers), which
  is why it is cached in the backend and fetched once per session by the frontend.
* `internal/platform/darwin` now runs a helper binary. The argument vector is fixed and absolute, and
  nothing goes through a shell.
* The value type is macOS-shaped (`BundleID` is empty elsewhere), which is why the port is a catalog
  of *applications* and not of *processes*: a platform that can only describe processes answers with
  `Supported: false` today, and the rule editor remains the general tool.
