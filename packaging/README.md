# Packaging

Release packaging for SingBoxUI. This directory holds the **static inputs** the
packaging scripts consume (entitlements, installer notes); the scripts live in
`scripts/` and are driven by `make package-macos` / `make package-windows`.

## Design rules

1. **Unsigned dev builds must always work.** With no signing environment
   variables set, `scripts/package-macos.sh` and `scripts/package-windows.ps1`
   produce unsigned artifacts and say so. CI only signs when the matching
   secrets exist (rewrite spec §74/§75).
2. **No credentials in the repository.** Signing material is read from the
   environment only — `APPLE_CERTIFICATE`, `APPLE_CERTIFICATE_PASSWORD`,
   `APPLE_ID`, `APPLE_PASSWORD`, `APPLE_TEAM_ID`, `KEYCHAIN_PASSWORD`,
   `WINDOWS_CERTIFICATE`, `WINDOWS_CERTIFICATE_PASSWORD`. Nothing is committed
   and nothing is echoed to logs.
3. **Artifacts land in `dist/`**, named
   `singboxui-<version>-<platform>-<arch>[-suffix].<ext>`.
4. **A release never bypasses tests.** `.github/workflows/release.yml` calls the
   test pipeline in `.github/workflows/ci.yml` first (`release.needs: ci`).

## macOS

* `macos/entitlements.plist` — hardened-runtime entitlements for the signed
  `.app`. The elevated helper is a separate binary launched through
  `osascript … with administrator privileges` (ADR 005), which is why the
  Apple-events entitlement is present.
* Pipeline: `scripts/build.sh -platform darwin/universal` → inject
  `singboxui-priv` into `Contents/MacOS/` (built for both architectures and
  `lipo`-joined, so the universal bundle stays universal) → `codesign --options
  runtime` on the helper **then** the app (nested code is signed explicitly;
  `--deep` is not used) → `notarytool submit --wait` → `stapler staple` →
  `hdiutil` UDZO `.dmg`.
* `build/darwin/Info.plist` is a project input, not build output: it carries
  `CFBundleIdentifier = com.larffxx.singboxui` and
  `LSMinimumSystemVersion = 13.0`, which must match the deployment target
  `scripts/build.sh` sets (`MACOSX_DEPLOYMENT_TARGET=13.0`, plus the
  `-mmacosx-version-min` CGO flags that stop Wails from asking the linker for
  10.13 while the Go toolchain's own objects are built for 13.0).

## Windows

* Pipeline (`scripts/package-windows.ps1`, one architecture per run):
  1. `wails build -platform windows/<arch> -clean -nsis` — compiles
     `build/bin/singboxui.exe` with the version metadata injected through
     `-ldflags`, and materialises `build/windows/installer/{project.nsi,wails_tools.nsh}`.
  2. `go build ./cmd/singboxui-priv` → `build/bin/singboxui-priv.exe`, next to the
     application executable: the helper is what runs elevated TUN operations, so
     the UI process never is (ADR 005).
  3. Authenticode-sign `singboxui.exe` and `singboxui-priv.exe` when
     `WINDOWS_CERTIFICATE` is set (`/fd SHA256 /tr <timestamp> /td SHA256`).
  4. Patch the generated `project.nsi` idempotently so the installer also ships
     the helper, and re-run `makensis`. Wails' own `wails.files` macro installs
     only the application executable, so this step is what puts the helper into
     `%LOCALAPPDATA%\Programs\SingBoxUI`; the uninstaller removes the whole
     directory. Because the re-run happens *after* step 3, the binaries inside
     the installer are signed.
  5. Sign the installer, then publish `*-app.exe` and `*-setup.exe` into `dist/`.
* `build/windows/` is generated by Wails on a Windows host and is not committed;
  the script fails with an explicit message if the installer is requested before
  those assets exist (pass `-NoInstaller` for a portable app-only build).
* Unsigned runs (no secrets in the environment) produce the same artifacts
  unsigned and say so.
